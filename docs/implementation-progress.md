### Phase 4 decisions that need your attention
- **Finance started read-only.** In Phase 4 it only showed figures. Recording payments, approving or rejecting quotes and sending invoices and quotes were added later (see Phase 5). Changing budgets still stays on the web app.
- **The financial summary is only partly shown.** The API adds up draft and void invoices, so its "expected income", "outstanding" and margin figures are overstated; the app shows collected, costs, profit and budget left from it and takes "owed to you" from the aging report instead. This is also wrong on the web dashboard (`backend-gaps.md` G27).
- **Approvers see who asked and the note, not what is being approved.** The API sends no amount or items, and the web page is just as blind. The inbox says this on screen and on the confirmation, rather than presenting a one-tap approval as if it were informed (G26).
- **A request decision is never repeated.** After a timeout the request is read back and the user's own step is checked.
- **A new task is never created twice.** After a timeout the project's TO DO tasks are searched for the same title created in the last two minutes; if that list is too long to be sure, the app says so.
- **A due date or estimate cannot be removed once set** (the API ignores a missing value). The edit form says so.
- **Only people with `tasks.*` see Edit task** (the API accepts nothing else); anyone with `tasks.create` can add tasks.

### Phase 5 decisions that need your attention
- **Site Supervisors can raise and approve purchase requests.** They hold `materials.*`, which the procurement API accepts for view, manage and approve. The server does not stop anyone approving their own request (G32), so the confirmation only adds "You raised this request yourself". Workers (`materials.log`) never see Purchasing.
- **Receiving deliveries is in the app; emailing an order to the supplier is not.** Receiving changes stock and is confirmed first. The API only sets an order's status to sent and contacts nobody, so the app can mark an order sent (saying so) but cannot email it.
- **Deciding a purchase request or order in the Requests inbox also moves the record** (the approvals engine updates its status, and an approved order becomes SENT; G34). The confirmation for an order says so, and the purchasing lists reload afterwards.
- **A request is never created twice.** After a timeout the newest own drafts are checked (own, created within two minutes, same item count); if none matches the message says nothing was created. If submitting fails after the draft was saved, the draft is kept and the message says so.
- **Rejecting replaces the requester's notes** with the reason (G31). The reject sheet says this before it is sent.
- **A delivery is the riskiest stock write.** The server adds to stock on every call and has no way to tell a repeat from a second delivery (G37), so the order is re-read first, every outstanding line is sent (0 for what did not arrive), more than is outstanding is refused, and after a timeout the order is read back for a delivery of its own (new, yours, recent, same quantities). Corrections to a recorded delivery and over-deliveries are on the web app.
- **Payments are cash and bank transfers only.** PayNow and EcoCash make the server charge the customer through the gateway, which is not something to do from a record screen (G40). The invoice is re-read, its status and balance checked (the server checks neither), the amount is kept to the cent, and nothing is resent: after a timeout the invoice is read back for a payment of its own. No note can be sent (the API forbids it). Owner, Project Manager and Accountant can do this by default.
- **Stage moves mirror the web app.** A completed or skipped stage cannot be reopened from the phone (the web app cannot either); "complete" is not offered on a stage that needs approval, because the server would allow it and skip the approval.
- **Equipment costs are never read.** The API sends each item's daily rate and purchase cost to everyone who can see equipment (G36); the app ignores them.
- **A return is checked before it is sent.** The server closes whatever assignment id it is given and frees the item (G35), so the app re-reads the item and returns only when that assignment is still the one open assignment. With two open assignments, or none in the recent list, the screen says to use the web app.
- **Equipment can be added, edited, retired and put into maintenance from the phone** (with `materials.manage`), and assigning needs access to projects (a project to choose).
- **Quantity limits are stricter than the server's** (the server allows zero and any length; the form wants a positive amount, a description up to 200 characters and a unit up to 20).

- **Only some writes are saved offline: clock in, clock out and material used.** Payments, deliveries, approvals and stage moves depend on the server's current state (a balance, what is outstanding, a status), so sending them later against stale data is the harm to avoid; creating records (requests, tasks, change requests, documents) cannot be told apart from a second one. Those stay online-only on purpose.
- **A saved event is sent exactly once.** Each carries the time it happened, to the millisecond, which the server stores. Nothing is sent again after an unanswered attempt until 60 seconds have passed and the server has been asked for that exact moment (an entry that started then, a log used then). A refusal is shown to the person and never retried on its own, and a refused clock-in holds back the clock-out after it.
- **Clock events saved offline need B7.** Without it a replayed clock-in would be stamped with the time it is sent, not the time it happened. The app turns the feature on only after seeing the server's `X-Offline-Writes` header (remembered, and re-read from every reply). The server flags such an entry as manual, so it goes through approval like any other, and refuses a time in the future or more than 7 days ago.
- **Signing out with unsent entries asks first.** An expired session keeps them (they are the person's own time and material, keyed to them) and they are sent when the same person signs in again.
- **Alerts are opt-in per person and per phone.** A notification can only open a screen inside the app (a path starting with a single slash; anything with a scheme or host is dropped), and the router still checks the person's permissions.
- **No labour cost ledger.** The project cost list shows material purchases and manual entries only.

### Decisions that differ from the original plan or need your attention
- **GPS on clock in/out is opt-in:** a switch on the Clock screen, off by default, never required to clock.
- **Comment and photo drafts are not stored in the database.** Comment text stays in the box if posting fails; a failed photo can be chosen again. Only task status changes are queued (the only idempotent write a worker makes).
- **Project choice for clocking in / material logging comes from the worker's assigned tasks plus their own time history** (no "my projects" endpoint exists).
- **Unit costs are never shown to workers**, and **project budgets / costs are never shown to anyone** in this phase (the API sends them to every `projects.view` holder; see `backend-gaps.md` G21).
- **The overview screens are gated on supervisory permissions, not on `projects.view`**, because Workers hold `projects.view` and B4 is not deployed (see `permission-matrix.md`).
- **Approvals needs both the approve right and the right to list everyone's time**; a role with only `timesheets.approve` gets no Approvals tab.
- **Decisions on time are never queued offline.** An approver must see current data, and a decision feeds payroll.
- **Today reads open tasks with four calls (one per open status, capped at 100 each)** because the API has no "not done" or date filter. It says when a cap was reached.
- **Weekly summary is requested with the worker's local Monday as an instant**, not a bare date (see `api-integration.md`).

### Safety rules the code enforces (each has tests; most were mutation-checked)
1. Clock in/out and material usage are never queued offline and never repeated blindly. After a timeout the server is asked what happened first; if it cannot be asked, the screen says the outcome is unknown.
2. A checklist toggle flips state on the server, so it is never retried; after an uncertain failure the task is re-read.
3. Task status changes are the only queued writes. A change the server refuses is shown to the user (Try again / Discard) and is not retried forever.
4. A refusal (403/404/400) is never replaced by cached data; only connection trouble falls back to the saved copy.
5. Cached data and queued changes are keyed by user and wiped on sign-out / session expiry.
6. Buttons lock while a request is running, so a double tap sends once.
7. Time approvals and task assignment only set a status / membership, so after a timeout they are sent **once** more; a second failure leaves the screen unchanged and reports the failure. They are never queued.
8. Approval entries and project models do not parse pay rates, labour cost or budgets.
9. Invoice payments are read without the gateway payload, and invoice clients without their address or phone.
10. A request decision, a clock event, a material usage and a new task are each sent at most once per tap; unknown outcomes are looked up, never guessed.
11. A purchase request is never created twice and a submit / approve / reject is never resent. After a timeout the server is read back (the newest own DRAFT for a create; the request itself for the rest) and the message says what it holds. A refusal is an answer: nothing is looked up to recover it.
12. Approve, Reject and Submit appear only with `materials.approve` / `materials.manage`, and the new-request form refuses a deep link without `materials.manage`.
13. The Requests inbox looks a purchase request or order up only for people who can read purchasing, and a failed or refused lookup shows nothing rather than a guess.
14. Equipment is never assigned twice and a return is never resent. Assigning is read back after a timeout (only an open assignment of mine, to this project, made in the last two minutes counts); returning re-reads the item first, closes only the one open assignment, and is read back after a timeout.
15. Assign and Mark returned appear only with `materials.manage` (assign also needs project access), and the assign form refuses a deep link without them.
16. A delivery is never resent. The order is re-read first (what is outstanding comes from the server now), every outstanding line is sent, more than is outstanding is refused, and after a timeout the order is read back: only a new delivery of the user's own, made recently, with exactly the quantities entered counts as theirs; any other new delivery is reported as a conflict.
17. A payment is never resent and never sent for a method the app does not record (only cash and bank transfer). The invoice is re-read and must be open with a balance; the amount cannot exceed the balance; after a timeout only a new, received payment of the same method and amount made in the last two minutes counts as the user's own.
18. A stage status is sent once more after an uncertain failure (it only sets a field); a stage approval is never resent and is read back after a timeout. One stage changes at a time.
19. Receive, pay and the stage moves each appear only with their own permission, the forms refuse a deep link without it, and two activations of a confirm button in the same frame open one confirmation.
